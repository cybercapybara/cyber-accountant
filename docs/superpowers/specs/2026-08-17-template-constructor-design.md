# Конструктор шаблонов документов — дизайн-спецификация

**Дата:** 2026-08-17
**Статус:** черновик, написан автономно по ранее утверждённым владельцем решениям
**Предыдущие фазы:** [P3 — документы, роли, суммы прописью](2026-08-15-p3-documents-roles-words-design.md) (v0.4.x), миграция docgen на Typst (v0.5.0)

## 1. Цель

Дать организации возможность заводить собственные шаблоны документов, а форму
ввода к ним получать автоматически — без правки кода и без выкладки релиза.

Утверждённые владельцем решения, из которых исходит эта спека:

- **Гибрид:** арендатору — блоки, владельцу площадки — исходный текст Typst.
- Форма ввода строится **динамически из шаблона**.
- Нужен набор заранее заготовленных переменных: `%НДС`, оклад сотрудника,
  ФИО директора, расчётные счета и подобные.

## 2. Что НЕ входит

- Редактирование десяти встроенных шаблонов на диске. Они остаются в
  репозитории и под гейтом `template-render` в CI. Организация может сделать
  **свою копию** и править её.
- Произвольный Typst для арендатора (см. §4.3 — почему).
- Конструктор схем налоговой отчётности. ФНО 910.00/300.00 порождают XML для
  СОНО, у них фиксированный формат, и рисовать их блоками нельзя.

---

## 3. Главное противоречие, которое решает эта фаза

Вся нынешняя гарантия качества документов — гейт `template-render`: четыре
слоя проверок против **фикстур, лежащих в репозитории**, плюс шесть намеренных
поломок, доказывающих, что гейт кусается. Пользовательский шаблон в
репозиторий не попадает никогда и этой проверки не проходит **по определению**.

Значит, конструктор обязан принести проверку с собой — иначе он молча
обнуляет то, ради чего строился гейт. Это и есть главная задача фазы, а не
редактор как таковой.

Ответ спеки: **блоки дают проверку бесплатно**. Если шаблон собран из блоков,
сервер знает, какие статические подписи в нём напечатаны и какие поля он
потребляет, — то есть может сгенерировать и `expected.txt`, и фикстуру, и
прогнать те же четыре слоя при сохранении (§9). Для сырого исходника такой
вывод невозможен, поэтому сырой режим и ограничен владельцем площадки.

## 4. Модель авторства

### 4.1 Режим «блоки» — для организаций

Шаблон — упорядоченный список блоков. Каждый блок типизирован и имеет
параметры. Набор блоков фиксирован кодом (не расширяется данными):

| Блок | Что печатает | Что объявляет |
|---|---|---|
| `header` | Заголовок документа и номер/дату | поля `number`, `date` |
| `parties` | Реквизиты сторон (продавец/покупатель, работодатель/работник) | ссылку на организацию и/или контрагента |
| `text` | Абзац текста с подстановками | использованные переменные |
| `table` | Таблицу позиций | массив `items[]` с колонками |
| `totals` | Итоги, НДС, сумму прописью | целочисленное поле-источник в тиынах |
| `signatures` | Подписи сторон | должности и ФИО |
| `spacer` / `pagebreak` | Отступ, разрыв страницы | ничего |

Блоки хранятся как JSON. Из них **порождается** исходник Typst — один раз, при
публикации версии, а не при каждом рендере. Это делает результат
воспроизводимым и позволяет посмотреть, что именно будет собрано.

### 4.2 Режим «исходник» — для владельца площадки

Прямой текст Typst. Доступен только администратору площадки (уровень
`AdminController`), **независимо от роли в организации**: владелец
организации — это не владелец инсталляции.

### 4.3 Почему арендатору не дан сырой Typst

Не потому, что Typst опасен сам по себе. Песочница здесь настоящая и это
проверено по коду: `RenderJob` создаёт отдельный каталог через `mkdtemp` на
каждый рендер, запускает `typst compile --root <этот каталог>` и оборачивает
всё в `/usr/bin/timeout 60`. Сети у Typst нет, шелла нет, `read`/`include`
замкнуты корнем.

Причины две, и обе про другое:

1. **Проверяемость.** Из сырого исходника нельзя вывести, какие подписи он
   обязан напечатать, — значит, нельзя автоматически построить `expected.txt`,
   а без него слой «потеря содержимого» не работает. Именно этот слой поймал
   реальный дефект акта при миграции на Typst.
2. **Размер последствий.** Ошибка в шаблоне арендатора — это молча кривой
   бухгалтерский документ у клиента, который заметят через месяц. Блоки не
   дают напечатать сумму, не выведенную сервером из числа.

## 5. Хранение

Новая таблица `document_templates` — org-scoped, версии неизменяемы:

```
id            uuid PK
org_id        uuid NULL        -- NULL == шаблон площадки, виден всем
slug          text             -- 'invoice', 'my-act', ...
version       int              -- 1, 2, 3...; (org_id, slug, version) unique
mode          text             -- 'blocks' | 'source'
blocks        jsonb NULL       -- источник правды для mode='blocks'
source        text             -- Typst; для blocks порождён, для source авторский
schema        jsonb            -- порождена (blocks) или авторская (source)
form          jsonb            -- метаданные формы: подписи ru/kk, порядок, группы
expected      text NULL        -- статические подписи; порождены для blocks
status        text             -- 'draft' | 'published' | 'archived'
created_by    uuid
created_at    timestamptz
```

Опубликованная строка не меняется никогда — правка создаёт новую версию. Это
та же дисциплина, что у `document_versions` в P3: документ, выпущенный вчера,
обязан оставаться воспроизводимым.

### 5.1 Порядок разрешения шаблона при рендере

1. шаблон организации (`org_id = <текущая>`, `slug`, последняя `published`);
2. шаблон площадки (`org_id IS NULL`);
3. встроенный шаблон с диска (`templates/docs/<slug>/vN/`).

Диск остаётся последним рубежом и не удаляется: встроенные шаблоны прогоняются
через CI-гейт на каждой сборке, и они же — образец для копирования.

`RenderJob` сегодня резолвит шаблон через `TemplateRegistry::latest(slug)`,
читающий диск. Фаза добавляет источник из БД **перед** ним, материализуя
`source` в тот же временный каталог как `main.typ`. Песочница, таймаут и
единственный вызов компилятора не меняются.

## 6. Форма ввода выводится из шаблона, а не пишется отдельно

Схемы встроенных шаблонов сегодня не содержат ни заголовков полей, ни языков:
в `invoice/v1/schema.json` у поля только `type`. Форма, построенная напрямую по
такой схеме, показала бы пользователю `total_tiyn`.

Поэтому источник формы — **блоки**, а не схема. Каждый блок объявляет свои
поля вместе с человеческими подписями (рус./каз.), типом виджета и порядком;
из этого порождаются одновременно и `schema` (для валидации на сервере), и
`form` (для отрисовки в SPA). Схема остаётся тем, чем была, — контрактом
валидации, а не описанием интерфейса.

**Производные поля в форму не попадают.** Это прямо следует из P3: сервер сам
выводит `total`, `total_words`, `vat_amount` из целочисленных тиынов
(`InputPolicy::apply_derived_amount`), а присланная клиентом строка — это 422
`not_allowed_override`. Конструктор обязан сохранить это свойство: блок
`totals` спрашивает **число**, а сумму прописью печатает сервер.

## 7. Каталог готовых переменных

### 7.1 Дыра, которую это закрывает

Проверка по коду показала, что просьба владельца про готовые переменные — не
про удобство. Сегодня реквизиты сторон в первичке **целиком присылает
клиент**: `definitions.party` в `invoice/v1/schema.json` содержит `name`,
`identifier`, `address`, `iik`, `bik`, `bank`, `kbe`, и сервер не подставляет
из них ничего. То есть в каждом счёте бухгалтер заново набирает собственные
банковские реквизиты, и никакой механизм не мешает двум документам одной
организации разойтись в номере счёта.

### 7.2 Чего не хватает в данных

Каталог нельзя построить поверх существующих таблиц: в `organizations` есть
только `bin`, `name`, `tax_regime`, `vat_payer`, `status` — **ни адреса, ни
директора, ни расчётных счетов**. Поэтому фаза обязана добавить их хранение:

- реквизиты организации: юридический адрес, ФИО и должность подписанта;
- расчётные счета — **отдельной таблицей**, а не колонками: счетов у ТОО
  бывает несколько (тенге и валюта), у каждого свой банк, БИК и КБе, и один
  из них помечается основным.

Без этого шага переменные `org.bank_accounts` и `org.director_name`
подставлять неоткуда, и вся §7 — пустое обещание.

### 7.3 Сам каталог

Переменные — не свободный текст, а типизированный каталог, объявленный в коде.
Блок ссылается на переменную по идентификатору, сервер разрешает её при
рендере из данных организации. Пользователь не вводит их руками и не может
разойтись с учётом.

| Идентификатор | Что подставляет | Источник |
|---|---|---|
| `org.name`, `org.bin` | Название и БИН | `organizations` (есть сегодня) |
| `org.address` | Юридический адрес | `organizations`, **колонку добавляет эта фаза** |
| `org.director_name`, `org.director_position` | Подписант | `organizations`, **добавляет эта фаза** |
| `org.bank_accounts`, `org.primary_account` | Расчётные счета (ИИК, банк, БИК, КБе) | **новая таблица, §7.2** |
| `org.vat_rate` | Ставка НДС на дату документа | `tax_rates` (не константа в тексте) |
| `employee.full_name`, `employee.position` | Сотрудник | `employees` |
| `employee.salary_tiyn` | Оклад, целое в тиынах | `employees` |
| `counterparty.*` | Реквизиты контрагента | `counterparties` |
| `doc.number`, `doc.date` | Номер и дата документа | форма |

Ставка НДС **обязана** браться из налогового движка с датой действия, а не
записываться в шаблон числом: спека §7.1 требует, чтобы ставки были данными, а
не кодом, и шаблон здесь не исключение.

## 8. Права

Матрица прав (`OrgPermissions.hpp`) — deny-by-default, поэтому новые ресурсы
надо объявить явно. Добавляются два, симметрично существующему делению
`documents` / `hr_docs`:

|  ресурс | owner | accountant | hr | viewer |
|---|---|---|---|---|
| `templates` | rw | rw | — | r |
| `hr_templates` | rw | rw | rw | r |

Режим `source` не выражается ролью организации вообще: он требует
администратора площадки. Это отдельная проверка, а не ещё одна колонка.

---

## 9. Проверка при сохранении — гейт, принесённый с собой

Публикация версии шаблона запускает те же четыре слоя, что и CI, но по
порождённым данным:

- **Фикстура** порождается из схемы (типы, обязательность, разумные значения);
  суммы — целые в тиынах, чтобы слой сумм имел настоящий источник.
- **`expected.txt`** порождается из блоков: статический текст блоков и есть
  список подписей, которые обязаны оказаться в PDF.
- Прогон: содержимое (суммы выводятся проверкой из тиынов), геометрия (рамки
  слов против полей), утёкший синтаксис, линии сквозь текст.
- Провал — публикация отклоняется с указанием, что именно потерялось.

Это не эквивалент CI-гейта, и притворяться иначе не нужно (§12).

## 10. API

```
GET    /api/v1/doc-templates                    существующий; дополняется источником шаблона
GET    /api/v1/doc-templates/{slug}/form        схема + метаданные формы для отрисовки
GET    /api/v1/org-templates                    список шаблонов организации
POST   /api/v1/org-templates                    создать черновик (в т.ч. копией встроенного)
PUT    /api/v1/org-templates/{id}               править черновик
POST   /api/v1/org-templates/{id}/preview       собрать PDF по тестовым данным, не публикуя
POST   /api/v1/org-templates/{id}/publish       прогнать гейт (§9) и опубликовать версию
DELETE /api/v1/org-templates/{id}               архивировать (не удалять: версии документов ссылаются)
GET    /api/v1/template-variables               каталог готовых переменных (§7)
```

## 11. Безопасность

- **Изоляция арендаторов.** Каждый запрос к шаблонам org-scoped, как и все
  репозитории (§5 главной спеки). Шаблон площадки (`org_id IS NULL`) доступен
  на чтение всем и на запись — только администратору площадки.
- **Компиляция.** Не меняется: свой `mkdtemp` на рендер, `--root` на него,
  `timeout 60`. Пользовательский `source` попадает в тот же каталог и теми же
  правами, что и встроенный.
- **Отказ в обслуживании.** Таймаут ограничивает время, но не память и не
  размер вывода. Фаза добавляет предел размера исходника, предел числа блоков
  и проверку размера получившегося PDF.
- **Утечка через `read`.** Внутри `--root` лежит только `input.json` и
  `main.typ` этого рендера, так что читать нечего. Это свойство обязано быть
  закреплено тестом, а не комментарием.

## 12. Честные ограничения

- Гейт при сохранении слабее CI: фикстура порождённая, а не написанная
  человеком, и она не покрывает граничных случаев (длинные названия,
  многостраничные таблицы, нулевые суммы), которые в репозитории покрыты
  отдельными фикстурами.
- Проверка присутствия подписи работает по документу целиком: повторяющаяся
  подпись замаскирует потерю одного вхождения. Это ограничение унаследовано и
  конструктором не лечится.
- **Отсутствующую** линию по-прежнему не ловит ничто.
- Режим `source` проверяется только геометрией и утёкшим синтаксисом:
  подписей вывести неоткуда. Владелец площадки при желании прикладывает
  фикстуру и `expected.txt` руками — тогда работают все четыре слоя.

## 13. Открытые вопросы

- Нужен ли арендатору предпросмотр в браузере без обращения к серверу
  (мгновенная отрисовка при перетаскивании блоков) — или достаточно кнопки
  «Собрать PDF». Решается в плане: первое требует Typst в WASM, второе — нет.
- Двуязычность блоков: печатать оба языка всегда или переключателем на
  документ. Кадровые шаблоны сегодня двуязычны, первичка — нет.
