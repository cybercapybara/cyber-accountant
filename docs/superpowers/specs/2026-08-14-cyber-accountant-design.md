# Cyber Accountant — дизайн-спецификация

Дата: 2026-08-14
Статус: утверждена (дизайн-ревью пройдено по секциям)
Репозиторий: github.com/cybercapybara/cyber-accountant

## 1. Резюме

Cyber Accountant — мультитенантный SaaS «полуавтономный бухгалтер» для ТОО в
Казахстане: функциональный аналог cabinet.mybuh.kz, построенный как AI-бэкенд.
Система ведёт учёт (двойная запись), считает налоги по НК РК-2026, генерирует
PDF-документы из LaTeX-шаблонов (от первички до кадровых), разбирает и ведёт
почтовую переписку организации, хранит документы в S3 и выполняет действия
автономно в рамках настраиваемых политик — всё остальное через явные апрувы
человека.

Стек: форк `moveeeax/cpp-rapid-rest-template` (Drogon C++20, PostgreSQL 15,
Redis 7, vcpkg/CMake, React SPA, Helm). Сборка релизов — только GitHub Actions.
Первый тенант — собственное ТОО (dogfooding), архитектура SaaS с первого дня.

## 2. Утверждённые решения

| Вопрос | Решение |
|---|---|
| Модель продукта | SaaS с первого дня; обкатка на собственном ТОО как первом тенанте |
| Автономия AI | Автономия с политиками: рутинные действия в лимитах — сам, остальное — approve; дефолт fail-closed |
| Госинтеграции в v1 | Генерация без подачи: ФНО (XML для СОНО + PDF), ЭСФ-данные, кадровые доки; подача вручную. Интеграции (ИС ЭСФ, подача ФНО, ЕСУТД, банки) — фазы после v1 через адаптеры |
| LLM | Claude API (tool use), весь трафик через cybercapybara-llm-guard (PII-фильтрация, аудит, лимиты) |
| Почта | Полный почтовый агент: IMAP-разбор входящих + исходящие по политикам, вложения → S3 → учёт |
| UI | React SPA из шаблона: дашборд, апрувы, документы, учёт, кадры, чат с агентом |
| Налоговые режимы v1 | СНР на основе упрощённой декларации + НДС (ФНО 910.00, 300.00); ОУР (100/200) — после v1 |
| Архитектура | A: модульный монолит на шаблоне (api + worker), llm-guard отдельным сервисом |

## 3. Цели и не-цели

### Цели v1

1. Полный жизненный цикл первички: создать/принять документ → проводка →
   печатная форма PDF → отправка контрагенту.
2. Налоги упрощёнки + НДС: расчёт до тиына, ФНО 910.00 и 300.00 в XML
   (для загрузки в СОНО/Кабинет НП) и в печатном PDF.
3. Зарплата и кадры: payroll с ИПН/ОПВ/ОПВР/СО/ОСМС/ВОСМС, трудовые договоры,
   приказы, отпуска; кадровые документы двуязычно (каз/рус).
4. Почтовый агент: разбор входящих, классификация, извлечение реквизитов из
   вложений, черновики проводок; исходящие письма по политикам.
5. AI-оркестратор с полной трассировкой и политиками автономии; очередь
   апрувов; чат; проактивные прогоны по расписанию (дедлайны ФНО,
   месячное закрытие).
6. Мультитенантность и изоляция данных с первого дня.

### Не-цели v1 (осознанно отложено)

- Подача в госсистемы (ИС ЭСФ API, СОНО/КНП submit, ЕСУТД) и работа с ЭЦП/НУЦ.
- Банковские API (выписка в v1 импортируется файлом).
- ОУР: ФНО 100.00/200.00, полный КПН.
- Биллинг тенантов, публичный онбординг, тарифы.
- ОФД/онлайн-касса, ТНВЭД-инструменты, вебинары и прочий контент mybuh.

Архитектурное требование: всё из списка не-целей подключается адаптерами без
перестройки ядра (см. §12).

## 4. Архитектура

Модульный монолит на базе шаблона. Два бинаря из шаблона:

- **api** — Drogon HTTP-сервис, `/api/v1`, SSE для чата агента;
- **worker** — обработчик Redis-очереди джобов: LaTeX-рендер, IMAP-поллинг,
  SMTP-отправка, прогоны агента, расчёты по расписанию. В образ worker
  добавляется TeX Live (или tectonic); образ api остаётся лёгким.

Доменные модули внутри `src/` (header-only, по ADR 0003 шаблона), каждый со
своим набором таблиц, репозиториев, сервисов и контроллеров:

```
src/
  tenancy/   — организации, membership, роли
  ledger/    — план счетов, проводки, контрагенты, документы, банк. операции
  tax/       — ставки/константы, расчёты, ФНО (XML + данные для PDF)
  payroll/   — расчёт зарплаты, payslips
  hr/        — сотрудники, договоры, приказы, отпуска
  docgen/    — реестр LaTeX-шаблонов, валидация входа, рендер-джобы
  mail/      — ящики, IMAP-поллер, входящие/исходящие, SMTP
  agent/     — оркестратор Claude, инструменты, policy engine, апрувы, чат
  files/     — S3-клиент, presigned URL, раскладка бакетов
```

Правило зависимостей: `agent` зависит от всех доменных модулей (они — его
инструменты); доменные модули не знают про `agent`; `docgen`/`files` — утилиты
нижнего уровня. Границы модулей проектируются так, чтобы любой модуль позже
выделялся в отдельный сервис без изменения контрактов (путь масштабирования
SaaS).

Внешние сервисы: PostgreSQL, Redis, S3-совместимое хранилище (MinIO в кластере
или Hetzner Object Storage — за единым S3-клиентом), llm-guard (отдельный
деплой; единственная точка выхода к Claude API).

## 5. Мультитенантность

- `organizations` (id, БИН, название, налоговый режим, признак плательщика НДС,
  реквизиты, статус) и `org_members` (user_id, org_id, роль).
- Роли: `owner` (всё, включая политики и секреты), `accountant` (учёт,
  документы, апрувы), `viewer` (чтение).
- Каждая доменная таблица несёт `org_id NOT NULL REFERENCES organizations`.
- Репозитории принимают org-scope обязательным параметром конструктора/метода;
  методов «выбрать без org» не существует. Это проверяется тестами.
- JWT шаблона расширяется claim'ом активной организации; middleware резолвит
  membership и роль на каждый запрос.
- S3-раскладка: `org/{org_id}/{inbox|generated|statements}/...` — префикс
  органично изолирует файлы тенантов.
- Биллинг и самостоятельная регистрация тенантов — вне v1; организации создаёт
  системный админ (админка шаблона).

## 6. Учётное ядро (`ledger`)

### 6.1 План счетов

`accounts`: типовой план счетов РК (приказ МФ РК №185, разделы 1000–8000)
загружается seed-миграцией как системный; тенант добавляет свои субсчета
(родитель — системный счёт). Поля: код, название (рус/каз), тип
(актив/пассив/доход/расход/капитал), признак валютного учёта.

### 6.2 Проводки — двойная запись, insert-only

- `journal_entries`: шапка (дата операции, описание, статус, ссылка на
  источник — документ/agent_run/пользователь).
- `journal_lines`: строки (счёт, дебет/кредит, сумма в тенге, сумма и код
  валюты при валютной операции, контрагент, признак/сумма НДС).
- Инвариант: по каждой проводке Σдебет = Σкредит; проверяется на уровне
  сервиса и CHECK-триггером.
- Статусы: `draft → posted → reversed`. Posted-запись неизменяема (UPDATE
  запрещён триггером); исправление — только сторно (новая проводка с обратными
  знаками и ссылкой `reverses_entry_id`).
- Это фундамент доверия к AI-агенту: агент может создавать только черновики
  либо (по политике `auto`) постить, но никогда не переписывает историю.

### 6.3 Контрагенты

`counterparties`: БИН/ИИН (валидация контрольного разряда), наименование,
адрес, банковские реквизиты (ИИК/БИК/КБЕ), признак резидентства, признак
плательщика НДС, контактные email (для связи с почтовым модулем).

### 6.4 Документы

`documents` — единый реестр первички любого происхождения:

- типы: счёт на оплату, АВР, накладная, счёт-фактура (печатная форма),
  акт сверки, доверенность, входящий документ (скан/PDF), банковская выписка,
  кадровый документ, ФНО (печатная форма), прочее;
- источник: `generated` (наш docgen), `uploaded` (загрузка в UI),
  `email` (вложение из почты);
- статусы: `inbox → recognized → linked → archived` (для входящих),
  `draft → final → sent` (для генерируемых);
- связь many-to-many с `journal_entries` (`document_entries`);
- файлы в S3, в БД — метаданные, ключ S3, checksum, MIME.

### 6.5 Банковские операции

`bank_statements` + `bank_transactions`: импорт выписки файлом (CSV и формат
выгрузки 1С/клиент-банков) в v1. Агент предлагает матчинг транзакция ↔
документ/контрагент (`match_suggestions`), человек подтверждает; подтверждённый
матч порождает черновик проводки. Банковские API — адаптер после v1.

## 7. Налоговый движок (`tax`)

### 7.1 Ставки и константы — только данные, никогда код

- `tax_rates`: вид платежа (НДС, СНР-упрощёнка, ИПН, ОПВ, ОПВР, СО, ОСМС,
  ВОСМС, соцналог при необходимости), ставка, `effective_from`,
  `effective_to`, регион (для региональных вариаций упрощёнки по НК-2026),
  источник (ссылка на статью НК).
- `tax_constants`: МРП, МЗП, пороги (регистрация по НДС — 40 млн ₸,
  порог упрощёнки — 600 000 МРП) с датами действия.
- Любой расчёт берёт значения на дату операции/периода. Смена ставки —
  миграция данных, не релиз кода. Наполнение v1 — константы НК РК-2026
  (НДС 16%, упрощёнка 4% базовая), проверяются по официальным источникам КГД
  на этапе имплементации и фиксируются в golden-тестах.

### 7.2 Расчёты

Модуль `tax` — чистые функции: (период, входные данные) → результат, без
побочных эффектов. Каждый выполненный расчёт сохраняется в `tax_calculations`
со снапшотом входных данных и использованных ставок — расчёт воспроизводим
и объясним (агент показывает «почему такая сумма»).

Расчёты v1:

- СНР-упрощёнка: доход за полугодие × ставка, распределение ИПН/соцналог,
  корректировки по НК;
- НДС: начисление/зачёт по проводкам с признаком НДС, сальдо к уплате;
- проверка порогов: превышение порога НДС-регистрации и порога упрощёнки —
  событие для агента (уведомление владельцу).

### 7.3 ФНО

- v1: **910.00** (упрощённая декларация, полугодие) и **300.00** (НДС,
  квартал).
- Выход в двух формах: XML для загрузки в СОНО/Кабинет налогоплательщика
  (валидируется против XSD-схем СОНО в тестах) и печатный PDF через docgen.
- `tax_filings`: период, форма, статус (`draft → generated → submitted_manually`),
  ссылки на XML/PDF в S3, снапшот расчёта.
- Календарь дедлайнов: справочник сроков сдачи/уплаты по формам; агент по
  расписанию напоминает и готовит черновик формы за N дней (N — политика).
- После v1: 100.00/200.00 (ОУР) — движок расширяется новыми формами без
  изменения ядра.

## 8. Зарплата и кадры (`payroll`, `hr`)

- `employees`: ИИН, ФИО, должность, оклад, дата приёма/увольнения, льготы
  (вычеты по ИПН), реквизиты для выплат.
- `labor_contracts`, `hr_orders` (приём, увольнение, отпуск, командировка,
  изменение оклада), `vacations` (график и остатки отпусков).
- `payroll_runs` (месяц × организация) → `payslips` по сотруднику: начисление,
  ИПН, ОПВ, ОПВР, СО, ОСМС, ВОСМС, к выплате. Все ставки — из `tax_rates`.
- Payroll-суммы попадают в сводную часть ФНО и порождают проводки по зарплате.
- Кадровые документы (договор, приказы) генерируются docgen двуязычно
  (каз/рус), как требует ТК РК. ЕСУТД — адаптер после v1.

## 9. Генератор документов (`docgen`)

- Шаблоны — LaTeX в репозитории: `templates/latex/<slug>/vN/` (template.tex +
  schema.json + fixtures/). Версия шаблона фиксируется в каждом
  сгенерированном документе.
- У каждого шаблона JSON Schema входных данных; вход валидируется до рендера —
  ошибка данных отличима от ошибки шаблона.
- Рендер — джоба в worker: контейнерный вызов XeLaTeX (TeX Live) с кириллицей
  и казахской латиницей/кириллицей; таймаут и лимит памяти на рендер;
  `\write18` и внешние ресурсы отключены (шаблоны самодостаточны).
- Выход: PDF → S3 (`generated/`), запись в `documents` (checksum, версия
  шаблона, снапшот входных данных — документ воспроизводим).
- Набор v1: счёт на оплату, АВР, накладная, счёт-фактура (печатная форма),
  акт сверки, доверенность, трудовой договор (каз/рус), приказы
  (приём/увольнение/отпуск), расчётный листок, печатные формы ФНО 910/300.
- CI: smoke-рендер каждого шаблона с его fixtures на каждом PR, трогающем
  `templates/` или `docgen`.

## 10. Почтовый модуль (`mail`)

- `mailboxes` per org: IMAP/SMTP-хост, порт, логин; пароли шифруются libsodium
  (sealed box), мастер-ключ — из env, в БД не хранится.
- Входящие: worker-джоба поллит IMAP (интервал — конфиг) → `inbound_emails`
  (заголовки, тело, message-id для дедупликации) → вложения в S3 (`inbox/`) →
  `documents(status=inbox)`.
- Разбор входящих — прогон агента: классификация (счёт поставщика / акт /
  требование или уведомление налоговой / банковское / контрагентское /
  спам), извлечение реквизитов из PDF/сканов (Claude vision через llm-guard),
  привязка к контрагенту, черновик проводки, при необходимости — черновик
  ответа.
- Исходящие: `outbound_emails` (черновик агента или человека) → policy engine →
  SMTP из worker. Типы v1: отправка счёта/АВР контрагенту, напоминание о
  задолженности, ответ на входящий запрос, уведомления владельцу.
- Вся переписка связывается с контрагентами и документами; треды видны в SPA.

## 11. AI-агент (`agent`)

### 11.1 Оркестратор

- Агентный цикл на Claude API (tool use); все запросы — через llm-guard
  (единственный egress к LLM): фильтрация PII/секретов, аудит, лимиты
  и бюджеты per org.
- Инструменты агента — типизированные обёртки над доменными сервисами:
  `ledger.query`, `ledger.draft_entry`, `ledger.post_entry`, `tax.calculate`,
  `tax.generate_filing`, `docgen.render`, `mail.draft`, `mail.send`,
  `hr.draft_order`, `payroll.run_draft`, `files.get`, `files.put`,
  `counterparties.upsert`, `approvals.request`. Агент не имеет сырого SQL
  и прямого доступа к БД/S3/кредам.
- Каждый вызов инструмента до исполнения проходит policy engine (§11.2).

### 11.2 Политики автономии

- `autonomy_policies` per org: тип действия × границы × режим
  (`auto` / `approve` / `forbid`).
- Границы: максимальная сумма, whitelist контрагентов, категория письма,
  тип документа, повторяемость операции (уже была одобренная такая же).
- Дефолт при отсутствии подходящей политики — **`approve` (fail-closed)**.
  `forbid` доступен для явных запретов (например, «никогда не отвечать на
  письма гос. органов автоматически»).
- Примеры: «повторяющийся счёт известному контрагенту до 500 000 ₸ — auto»,
  «проведение проводки свыше лимита — approve», «любое письмо в адрес
  налоговых органов — approve».
- `approval_requests`: payload действия + человекочитаемый diff, канал
  уведомления, дедлайн; решение (approve/reject + комментарий) возвращается
  в прогон агента. Инбокс апрувов — в SPA.

### 11.3 Трассировка и триггеры

- `agent_runs` + `agent_steps`: полный трейс (промпты, tool calls, ответы,
  токены, стоимость) каждого прогона; просмотр в UI; ссылка из каждой
  созданной агентом сущности (`created_by_run_id`).
- Триггеры: расписание (ежедневный разбор почты, месячное закрытие, календарь
  дедлайнов ФНО), события (новое письмо, новый документ, превышение
  налогового порога), явный запрос из чата.
- Чат: `conversations`/`messages`, стриминг ответов по SSE в SPA; из чата
  доступны те же инструменты с теми же политиками.

## 12. Интеграции после v1 — контракт адаптеров

Ядро определяет порты (интерфейсы), реализации подключаются фазами:

- `EsfGateway` — выставление/приём ЭСФ в ИС ЭСФ (ЭЦП тенанта);
- `FilingGateway` — подача ФНО (СОНО/КНП);
- `LaborRegistry` — ЕСУТД (Enbek);
- `BankFeed` — автоматическая выписка;
- v1-реализация каждого порта — `ManualGateway`: генерирует артефакт и
  инструктирует человека (статус `submitted_manually`).

Работа с ЭЦП/НУЦ РК проектируется в фазе интеграций отдельной спекой
(хранение ключей тенанта — отдельный контур безопасности).

## 13. API

- Все бизнес-роуты под `/api/v1`, OpenAPI-first, triple-sync (контроллер +
  `Endpoints.hpp` + `openapi.yaml`), единый формат ошибок
  `{error, status, message}` — конвенции и CI-гейты шаблона.
- Ресурсные группы: `orgs`, `counterparties`, `documents`, `journal-entries`,
  `accounts`, `bank-statements`, `taxes` (calculations, filings, rates),
  `payroll`, `employees`, `hr-orders`, `mailboxes`, `emails`, `templates`,
  `files` (presigned upload/download), `agent` (runs, chat SSE), `approvals`,
  `policies`.
- Новые ресурсы скаффолдятся `scripts/new-resource.sh` — миграция + DTO +
  репозиторий + контроллер + OpenAPI + интеграционный тест по построению
  проходят гейты.
- SPA: разделы Дашборд (дедлайны, апрувы, сальдо), Документы, Учёт (проводки,
  контрагенты, банк), Налоги (расчёты, ФНО), Зарплата/Кадры, Почта, Агент
  (чат + трейсы прогонов), Настройки (политики, ящики, участники). Клиент
  генерируется из OpenAPI (openapi-typescript), UI — shadcn/ui из шаблона.

## 14. Безопасность

- AuthN/AuthZ: JWT + RBAC шаблона, расширенные org-membership (§5).
- Секреты тенантов (IMAP/SMTP, позже ЭЦП): libsodium sealed box, мастер-ключ
  из env; ротация ключа — регенерацией записей.
- Audit trail шаблона расширяется: каждая мутация имеет актора — user_id или
  agent_run_id; действия агента дополнительно видны в трейсе прогона.
- LLM-контур: llm-guard — единственный egress; в промпты не попадают креды
  и мастер-ключи; инструменты — единственный канал воздействия агента на
  систему; policy engine — единственный канал выполнения необратимых действий.
- Файлы: только presigned URL с TTL, публичных ссылок нет; бакеты приватные.
- Гейты шаблона: gitleaks, Trivy, rate limiting, idempotency-keys на мутациях.

## 15. Тестирование

Поверх гейтов шаблона (clang-format/tidy, ASan/UBSan/TSan, OpenAPI drift,
test buckets, gitleaks, Trivy, helm-render):

1. **Налоговый движок — golden-тесты**: фиксированные примеры расчётов по
   официальным разъяснениям/калькуляторам КГД; движок обязан воспроизводить
   их до тиына. Каждая смена ставок = новые golden-фикстуры с датами.
2. **ФНО XML** — валидация против XSD-схем СОНО на фикстурах.
3. **LaTeX** — smoke-рендер всех шаблонов с их fixtures в CI; PDF → текст →
   snapshot-сравнение ключевых полей.
4. **Policy engine** — таблично-управляемые тесты (действие × политика →
   auto/approve/forbid), включая fail-closed дефолт и границы сумм.
5. **Учётные инварианты** — property-тесты: баланс проводок, неизменяемость
   posted, корректность сторно, org-изоляция репозиториев.
6. **Агентные evals** — фикстурные письма/сканы → ожидаемая классификация и
   извлечённые реквизиты; отдельный workflow по флагу (стоимость LLM), не
   гейтит каждый PR; прогоняется перед релизом.

## 16. Сборка и деплой

- Сборка релизов — **только GitHub Actions**: образы `api`, `worker`
  (+TeX Live), `frontend`; amd64 + arm64; vcpkg warm-cache шаблона; Trivy.
  Локально — только `make ci-local` для отладки, релизные артефакты локально
  не собираются.
- Деплой: Helm-чарты шаблона (api, worker, frontend, umbrella) в Talos-кластер
  на Hetzner (`cluster/`); llm-guard — отдельный релиз рядом; MinIO — в
  кластер тем же umbrella-чартом либо Hetzner Object Storage (решение на
  этапе P0; код не меняется — единый S3-клиент).
- Конфигурация: `config/config.json` c `${VAR}`-плейсхолдерами + env,
  `make prod-check` перед прод-профилем — конвенции шаблона.
- Наблюдаемость из шаблона: Prometheus-метрики (+ новые: очередь апрувов,
  латентность рендера, стоимость LLM per org), OTLP-трейсинг, structured logs.

## 17. Фазы реализации

Каждая фаза — отдельный цикл «план → реализация» (writing-plans), каждая
завершается работающим инкрементом в кластере.

- **P0 — скелет**: перенос шаблона в `cyber-accountant`, удаление демо,
  мультитенантность (organizations, membership, org-scoped репозитории,
  JWT-claim), CI зелёный, деплой umbrella в кластер, выбор S3-бэкенда.
- **P1 — учётное ядро**: план счетов (seed), проводки + инварианты,
  контрагенты, документы, S3/files, docgen + 5 шаблонов первички
  (счёт, АВР, накладная, счёт-фактура, акт сверки).
- **P2 — налоги и люди**: tax_rates/constants (НК-2026), расчёты упрощёнки и
  НДС, ФНО 910/300 (XML + PDF), payroll, hr + кадровые шаблоны (каз/рус),
  календарь дедлайнов.
- **P3 — почта**: mailboxes + шифрование кредов, IMAP-поллер, входящий
  пайплайн (вложения → S3 → documents), исходящие через SMTP, импорт
  банковской выписки.
- **P4 — AI**: оркестратор через llm-guard, инструменты, policy engine,
  approvals-инбокс, чат (SSE), трейсы прогонов, триггеры по расписанию и
  событиям, агентные evals.
- **P5+ — за пределами v1**: ИС ЭСФ → подача ФНО → ЕСУТД → банки (порты из
  §12), биллинг тенантов, ОУР (ФНО 100/200), онлайн-касса/ОФД.

Система полезна уже после P2 (считает налоги и печатает документы);
AI-слой ложится на готовое, оттестированное ядро.

## 18. Риски

| Риск | Митигация |
|---|---|
| Ставки/формы НК РК-2026 меняются и уточняются | Всё таблично с датами действия; golden-тесты фиксируют текущее прочтение; смена ставки — миграция данных |
| XSD/форматы СОНО недокументированы публично | Схемы добываются из СОНО-клиента на этапе P2; до подтверждения XML помечается как экспериментальный, PDF — основной артефакт |
| Ошибки агента в учёте | Insert-only + сторно, fail-closed политики, полный трейс, апрувы на необратимое |
| TeX Live раздувает worker-образ | Отдельный образ worker; api не затронут; кэш слоёв в GHCR |
| Стоимость LLM при разборе почты | Бюджеты per org в llm-guard; классификация дешёвой моделью, глубокий разбор — дорогой только по необходимости |
| Один разработчик, большой охват | Жёсткая фазировка P0–P4; генераторы шаблона; каждая фаза шипается независимо |

## 19. Открытые вопросы (решаются в своих фазах)

- MinIO в кластере vs Hetzner Object Storage — P0, по результату проверки
  ресурсов кластера.
- tectonic vs полный TeX Live для рендера — P1, по результату smoke-рендера
  шаблонов с казахской типографикой.
- Точный перечень региональных ставок упрощёнки — P2, по официальным
  публикациям КГД/маслихатов.
