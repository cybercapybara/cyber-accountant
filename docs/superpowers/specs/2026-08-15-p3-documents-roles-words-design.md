# P3: суммы прописью, жизненный цикл документов, роль кадровика, навигация

**Дата:** 2026-08-15
**Статус:** утверждено владельцем
**Предыдущая фаза:** [P2 — налоги, зарплата, кадры](2026-08-14-cyber-accountant-design.md) (релиз v0.3.0)

## 1. Цель

Четыре независимых улучшения поверх существующей архитектуры, каждое —
самостоятельная ценность:

1. Сумма прописью считается сервером из числа, а не присылается клиентом.
2. Документы редактируются с сохранением версий; удаление разграничено с
   аннулированием.
3. Появляется роль **кадровика** с правами на кадровый контур.
4. Верхнее меню сворачивается из девяти плоских пунктов в четыре раздела.

## 2. Что НЕ входит

- **Миграция docgen с LaTeX на Typst** — отдельная фаза, решение записано
  вместе с аргументами; делается ДО конструктора шаблонов.
- **Конструктор шаблонов** (редактирование шаблонов, динамические формы по
  схеме, реестр заготовленных переменных) — своя спека, гибридная модель:
  блоки для арендаторов, сырой Typst только для владельца инстанса.

Эта фаза не трогает шаблоны сверх минимума и не меняет движок рендера.

## 3. Сумма прописью

### 3.1 Зачем это не только удобство

Сейчас `tax_words`, `net_words`, `balance_words`, `salary_words` приходят из
тела запроса. В P2 выяснилось, что клиентские поля в документах — вектор
подделки: `document_input` без allowlist позволял выпустить PDF декларации с
балансом 1 ₸ при правдивом XML той же записи. Дыру закрыли allowlist'ом, а
`sales_tenge` убрали совсем — оборот выводится из проводок.

Сумма прописью выводится из числа однозначно. Значит, она обязана считаться
сервером, и расхождение цифры и текста в одном документе становится
невозможным **по построению**, а не по дисциплине.

### 3.2 Модуль

`src/money/AmountInWords.hpp` — чистый, без БД и без Drogon, тестируется в
`tests/unit`.

```
namespace Money {
    std::string to_words_ru(long long tiyn);
    std::string to_words_kk(long long tiyn);
}
```

Вход — целые тиыны (как везде в системе; плавающая точка в денежном пути
запрещена). Отрицательные — `std::invalid_argument`: документ с отрицательной
суммой прописью не имеет смысла, знак принадлежит контексту («к возврату»).

### 3.3 Русский

Согласование обязательно:

- единицы 0-19, десятки, сотни;
- разряды: **тысяча** — женский род («одна тысяча», «две тысячи», «пять
  тысяч»), **миллион** и **миллиард** — мужской («один миллион», «два
  миллиона», «пять миллионов»);
- правило окончаний: 1 → ед. ч.; 2-4 → род. п. ед. ч.; 0 и 5-20 → род. п.
  мн. ч.; для 11-14 всегда мн. ч. («одиннадцать тысяч»);
- **тенге не склоняется** — в казахстанской деловой практике всегда «тенге»;
- тиыны выводятся числом двумя цифрами, не прописью: `«... тенге 00 тиын»`;
- первая буква заглавная.

Примеры (обязательные golden-векторы):

| тиыны | результат |
|---|---|
| 0 | Ноль тенге 00 тиын |
| 1 | Ноль тенге 01 тиын |
| 100 | Один тенге 00 тиын |
| 20000000 | Двести тысяч тенге 00 тиын |
| 2100000 | Двадцать одна тысяча тенге 00 тиын |
| 200000 | Две тысячи тенге 00 тиын |
| 500000 | Пять тысяч тенге 00 тиын |
| 1100000 | Одиннадцать тысяч тенге 00 тиын |
| 25057500 | Двести пятьдесят тысяч пятьсот семьдесят пять тенге 00 тиын |
| 100000000000 | Один миллиард тенге 00 тиын |

Вектор `25057500` — это net из смоук-теста v0.3.0 (250 575,00 ₸ при окладе
300 000 ₸), чтобы спека была связана с реальными данными системы.

### 3.4 Казахский

Числительные не согласуются по родам и не имеют падежных окончаний во
множественном числе — язык агглютинативный, разряд просто приписывается:
`екі жүз мың теңге`. Это существенно проще русского, но **требует сверки
носителем** перед выпуском: цена ошибки — юридический документ.

Разряды: `мың` (тысяча), `миллион`, `миллиард`. Формат тот же:
`«... теңге 00 тиын»`.

### 3.5 Интеграция

- Из серверных allowlist'ов (`fno_910`, `fno_300`, `payslip`, кадровые)
  убираются все `*_words`. Попытка прислать — `422 not_allowed_override`,
  тем же механизмом, что уже работает.
- Значение выводится из той же суммы, которая идёт в XML и в проводку.
- Двуязычные кадровые шаблоны получают обе строки: русскую и казахскую.
- SPA перестаёт показывать поля ввода прописи; соответствующие подсказки
  убираются (устаревший поясняющий текст — тоже дефект).

## 4. Документы: версии, правка, удаление

### 4.1 Текущее состояние

Документ — это строка в `documents` с `input_snapshot` (JSON, чем его
отрендерили) плюс объект в S3. Правки нет; удаления нет.

### 4.2 Правка = новая версия

Правка меняет `input_snapshot` и порождает **новую версию** с новым рендером.
Предыдущий PDF остаётся в объектном хранилище и доступен в истории.

Причина именно такой модели: бухгалтерский документ — свидетельство. Тихая
перезапись файла, на который кто-то мог сослаться, разрывает аудиторский
след. Хранение лишних PDF дешевле, чем невозможность объяснить расхождение.

Версии нумеруются в пределах документа; текущая помечена явно. Каждая версия
хранит, кто и когда её создал.

### 4.3 Удаление против аннулирования

Разделение диктуется тем, что журнал проводок **insert-only** и правится
только сторно — это фундамент всей системы:

- **Черновик, не привязанный к проведённой проводке** — удаляется физически.
  Право: `owner`, `accountant`; кадровик — только документы кадрового типа.
- **Документ, привязанный к проведённой проводке** — не удаляется никогда.
  Доступно аннулирование: статус `void`, документ остаётся видимым с явной
  пометкой. Отмена самой проводки — отдельное действие (сторно), у него уже
  есть свой механизм.

### 4.4 Побочно: организация не удаляется

При релизе v0.3.0 выяснилось: `journal_entries_immutability()` запрещает
любое удаление непроведённой записи и **не имеет исключения для каскада**,
хотя соседний триггер `journal_lines_frozen_after_post()` такое исключение
имеет и прямо называет каскад организации легальным. В результате
`ON DELETE CASCADE` недостижим и арендатора невозможно отключить штатно —
при очистке тестовых данных пришлось временно отключать триггер.

Это чинится здесь же, вместе с семантикой удаления документов: триггеру
нужно то же исключение для каскада, что у его собрата.

## 5. Роль кадровика

### 5.1 Модель ролей

Сейчас роли — `owner`, `accountant`, `viewer`, зашиты в `CHECK` миграции 006
и в `Tenancy::Organization`. Добавляется `hr`.

### 5.2 Права

Владелец решил: **оклад кадровик видит, расчёты — нет.** Обоснование: он
готовит трудовые договоры и приказы, где оклад — обязательное поле; без него
кадровик не сможет сделать свою основную работу.

| Ресурс | owner | accountant | hr | viewer |
|---|---|---|---|---|
| Сотрудники (вкл. оклад) | CRUD | CRUD | CRUD | чтение |
| Трудовые договоры, приказы, отпуска | CRUD | CRUD | CRUD | чтение |
| Кадровые документы | CRUD | CRUD | CRUD | чтение |
| Расчётные листки, прогоны зарплаты | CRUD | CRUD | — | чтение |
| Проведение зарплаты в учёт | да | да | — | — |
| Журнал проводок | CRUD | CRUD | — | чтение |
| Контрагенты, первичные документы | CRUD | CRUD | — | чтение |
| Налоги, расчёты, ФНО | CRUD | CRUD | — | чтение |
| Участники организации | CRUD | — | — | — |

«—» означает **невидимо**, а не «только чтение»: кадровик не должен видеть
зарплатные ведомости и налоговую отчётность.

### 5.3 Риск, который надо снять явно

Текущий RBAC грубый: по сути «viewer не пишет». Если добавить роль, не
введя явной матрицы «роль × ресурс × действие», кадровик по умолчанию
получит доступ к журналу и налогам. Поэтому проверка прав должна стать
явной и покрытой тестами **на отказ** — для каждого закрытого ресурса тест,
что кадровик получает 403, а не 200.

Это ровно тот класс ошибки, который в P2 дал утечку через `merge_patch`:
механизм существовал, но не был применён везде.

## 6. Навигация

Сейчас в авторизованном меню девять плоских пунктов. Группировка:

- **Учёт** — журнал проводок, документы, контрагенты
- **Кадры и зарплата** — сотрудники, кадры, зарплата
- **Налоги** — налоги (расчёты, сроки, ФНО)
- **Настройки** — организации, администрирование, аудит

Пункты и разделы фильтруются по роли: кадровик видит один раздел, а не
девять чужих. Раздел, у которого не осталось видимых пунктов, не рисуется.

Маршруты и меню живут одним массивом (`routes/manifest.tsx`) — это
сознательное решение против расхождения; группировка добавляется туда же,
а не отдельной структурой.

## 7. Миграции

- расширение `CHECK` роли до `('owner','accountant','hr','viewer')`;
- версионирование документов;
- статус `void` и мягкое состояние документа;
- исключение для каскада в триггере неизменяемости журнала.

Нумерация продолжает существующую последовательность, без `BEGIN`/`COMMIT`
(раннер оборачивает сам).

## 8. Тестирование

- Прописью: golden-векторы из §3.3 плюс краевые (0, 1 тиын, ровно 1 тенге,
  11-14, границы разрядов) — юнит, без сервисов.
- Права: для каждого закрытого для кадровика ресурса — тест на **403**.
- Версии: правка порождает версию, старый PDF остаётся доступен.
- Удаление: черновик удаляется; привязанный к проведённой проводке —
  отказ с 409 и возможность аннулировать; каскад организации работает.
- Прописью не принимается от клиента: попытка прислать `*_words` → 422.

## 9. Инварианты, которые фаза не имеет права нарушить

Наследуются из P0-P2 и обязательны:

- деньги — целые тиыны, никакой плавающей точки;
- ставки и константы только из `tax_rates`/`tax_constants`, никогда в коде;
- `org_id` только из JWT, каждый запрос ограничен организацией;
- журнал insert-only, правится только сторно;
- 400 — форма, 422 — значение, 409 — состояние;
- тройная синхронизация маршрутов (контроллер, `Endpoints.hpp`, OpenAPI);
- весь пользовательский текст — русский;
- сборки только в GitHub Actions;
- коммиты без AI-атрибуции.
