# P3: суммы прописью, жизненный цикл документов, роль кадровика, навигация

**Дата:** 2026-08-15 (ревизия 2 — после критики спеки против кода)
**Статус:** утверждено владельцем; ревизия 2 сделана автономно по результатам
независимой проверки утверждений спеки по исходникам
**Предыдущая фаза:** [P2 — налоги, зарплата, кадры](2026-08-14-cyber-accountant-design.md) (v0.3.0/v0.3.1)

## 1. Цель

Четыре улучшения поверх существующей архитектуры:

1. Сумма прописью считается сервером из числа, а не присылается клиентом.
2. Документы редактируются с версиями; удаление разграничено с аннулированием.
3. Появляется роль **кадровика**.
4. Верхнее меню сворачивается из десяти плоских пунктов в четыре раздела.

## 2. Что НЕ входит

- **Миграция docgen на Typst** — отдельная фаза, ДО конструктора шаблонов.
- **Конструктор шаблонов** — своя спека, гибридная модель.

**Ревизия 2:** первая редакция утверждала «шаблоны не трогаем». Это неверно.
Поля `total_words` объявлены **обязательными** в схемах `invoice`, `avr`,
`waybill`, `tax_invoice`, а суммы там хранятся строками — целого значения на
сервере не существует. Фаза обязана добавить целочисленные поля в 4
`schema.json`, обновить 8 фикстур и прогнать гейт `template-render`.

## 3. Сумма прописью

### 3.1 Зачем это не только удобство

В P2 клиентские поля документов дали настоящую дыру: `document_input` без
allowlist позволял выпустить PDF декларации с балансом 1 ₸ при правдивом XML
той же записи. Дыру закрыли, `sales_tenge` убрали совсем.

Сумма прописью выводится из числа однозначно, значит обязана считаться
сервером. Тогда расхождение цифры и текста в одном документе становится
невозможным **по построению**.

### 3.2 Модуль

`src/money/AmountInWords.hpp` — чистый, без БД и Drogon, тесты в `tests/unit`.

```
namespace Money {
    std::string to_words_ru(long long tiyn);   // ожидает НЕОТРИЦАТЕЛЬНОЕ
    std::string to_words_kk(long long tiyn);
}
```

**Знак.** Обе функции принимают только неотрицательное; отрицательное —
`std::invalid_argument`. Вызывающий обязан передать модуль. Это не
формальность: `TaxController::build_form_input` считает `balance_tenge` для
ФНО 300.00 **по модулю**, а знак несёт отдельное поле `balance_kind`
(к уплате / к возврату). Без этого правила первая же декларация с НДС к
возврату уронит рендер-джобу.

**Верхняя граница.** Разряды поддерживаются до **триллиона** включительно
(10^14 тиын = 10^12 ₸) — та же граница, что уже введена в
`Payroll::kMaxGrossTiyn`. Выше — `std::out_of_range`, на уровне API → 422.

### 3.3 Русский

- единицы 0-19, десятки, сотни;
- разряды: **тысяча** — женский род («одна тысяча», «две тысячи», «пять
  тысяч»); **миллион**, **миллиард**, **триллион** — мужской;
- окончания: 1 → ед. ч.; 2-4 → род. п. ед. ч.; 0 и 5-20 → род. п. мн. ч.;
  для 11-14 **всегда** мн. ч.;
- **тенге не склоняется**;
- тиыны — числом, всегда две цифры: `«... тенге 07 тиын»`;
- первая буква заглавная;
- принято написание **«Ноль»** (не «Нуль»).

Обязательные golden-векторы:

| тиыны | ₸ | результат |
|---|---|---|
| 0 | 0,00 | Ноль тенге 00 тиын |
| 1 | 0,01 | Ноль тенге 01 тиын |
| 5 | 0,05 | Ноль тенге 05 тиын |
| 67 | 0,67 | Ноль тенге 67 тиын |
| 100 | 1,00 | Один тенге 00 тиын |
| 20000000 | 200 000,00 | Двести тысяч тенге 00 тиын |
| 2100000 | 21 000,00 | Двадцать одна тысяча тенге 00 тиын |
| 200000 | 2 000,00 | Две тысячи тенге 00 тиын |
| 500000 | 5 000,00 | Пять тысяч тенге 00 тиын |
| 1100000 | 11 000,00 | Одиннадцать тысяч тенге 00 тиын |
| 11100000 | 111 000,00 | Сто одиннадцать тысяч тенге 00 тиын |
| 25057500 | 250 575,00 | Двести пятьдесят тысяч пятьсот семьдесят пять тенге 00 тиын |
| 1000000000 | 10 000 000,00 | Десять миллионов тенге 00 тиын |
| 200200200 | 2 002 002,00 | Два миллиона две тысячи два тенге 00 тиын |

Четыре последних — не украшение, а именно те места, где конвертеры ломаются:
пустая средняя триада («десять миллионов», а не «десять миллионов ноль
тысяч»), согласование мужского и женского рода **в одном числе**, 11-14 не в
начале триады, и тиыны, отличные от нулей. Вектор `25057500` — реальный net
из смоук-теста v0.3.0 при окладе 300 000 ₸.

### 3.4 Казахский

Владелец выбрал «сразу русский и казахский». Правила (первая редакция спеки
описывала их неверно, будто разряд просто приписывается):

- 0 нөл, 1 бір, 2 екі … 10 он; 20 жиырма, 30 отыз, 40 қырық, 50 елу,
  60 алпыс, 70 жетпіс, 80 сексен, 90 тоқсан; 100 жүз, 1000 мың;
- согласования по родам нет, падежных окончаний во множественном нет;
- **единица опускается перед `жүз` и `мың`**: 100 → `жүз`, 1000 → `мың`
  (не `бір жүз`, не `бір мың`), но 200 → `екі жүз`, 2000 → `екі мың`;
- **перед `миллион`/`миллиард` единица НЕ опускается**: `бір миллион`;
- формат: `«... теңге 07 тиын»`.

**Гейт качества:** казахские векторы обязаны быть выведены из цитируемых
источников по казахским числительным, а не сочинены реализующим агентом,
иначе реализация становится собственным оракулом. До проверки носителем
казахский вывод считается предварительным; на русскую первичку и ФНО это
не влияет — они разблокированы независимо.

Двуязычный `labor_contract` печатает `salary_words` в **обеих** половинах,
русской и казахской. Значит нужно отдельное поле `salary_words_kk` в схеме,
фикстурах и шаблоне.

### 3.5 Интеграция — полный список мест

Пропуск любого из них = 422 в проде.

**Серверные allowlist'ы** (`fno_910`, `fno_300`, `payslip`, кадровые):
все `*_words` убрать, значение выводить.

**`POST /documents/generate` — отдельный случай, и он тяжелее.** У этого
маршрута allowlist'а нет вообще: весь `input` приходит от клиента. Схемы
`invoice`, `avr`, `waybill`, `tax_invoice` требуют `total_words`, а сумма в
них — строка (`"total": {"type":"string"}`). Целого значения на сервере нет,
и выводить прописью из строки «12 345,67» запрещено: это парсинг обратно в
деньги мимо инварианта целых тиын.

Поэтому: в 4 схемы добавляется целочисленное поле (`total_tiyn`; для
`tax_invoice` — `totals.with_vat_tiyn`), сервер считает и `total`, и
`total_words` из него, а клиентские `total_words` отвергаются.

**Дефект, найденный при релизе v0.3.1 и чинящийся здесь же:** сейчас
`POST /documents/generate` отвечает **500** для слагов `payslip`, `fno_910`,
`fno_300`, `hr_order`, `labor_contract`. OpenAPI ограничивает `template_slug`
пятью слагами первички, но код это не проверяет: слаг проходит насквозь как
`doc_type` и падает на `documents_doc_type_check`. Должно быть **422** с
понятным сообщением. Строк-сирот не остаётся — транзакция откатывается.

**Точка внедрения** (важна для будущей миграции на Typst): прописи
подставляются сервером в **JSON `input`**, шаблон продолжает содержать
placeholder `{{ total_words }}`. Считать прописи внутри шаблона или переносить
поле из схемы в шаблон запрещено — иначе миграция на Typst будет это
разбирать обратно.

**SPA:** `GenerateDocument.tsx` (4 формы), `Taxes.tsx`, `HrOrders.tsx`,
`lib/schemas/payroll.ts` и их тесты — поля ввода прописи убираются вместе с
пояснительными подсказками.

## 4. Документы: версии, правка, удаление

### 4.1 Правка = новая версия

Правка порождает новую версию с новым рендером; предыдущий PDF остаётся.
Бухгалтерский документ — свидетельство: тихая перезапись файла, на который
могли сослаться, рвёт аудиторский след.

**Схема.** `s3_key`, `checksum`, `mime`, `size`, `input_snapshot`,
`template_version` переезжают в `document_versions`; `documents` хранит
указатель на текущую версию. Версии по отдельности не удаляются — удаление и
аннулирование действуют на документ целиком.

**Правка обязана соблюдать тот же allowlist, что и создание.** Это прямое
следствие §3.1: `input_snapshot` — ровно то, что рендерит джоба, поэтому
приём его целиком заново открывает дыру подделки, которую мы закрыли.
Документы с `source` = `uploaded`/`email` не редактируются (у них
`input_snapshot` пуст по построению) — 409.

**Что ломается и должно быть починено вместе:**

1. `POST /documents/{id}/download-url` читает `documents.s3_key` — появляются
   `GET /documents/{id}/versions` и скачивание конкретной версии
   (каждый маршрут — тройная синхронизация: контроллер, `Endpoints.hpp`,
   OpenAPI).
2. `RenderJob` делает `set_file` + `set_status('final')` без проверки
   состояния. На аннулированном документе это снимет аннулирование, а
   повторный запуск перезапишет файл текущей версии. `set_file` должен
   ключеваться по `version_id`, а джоба — не делать ничего для
   аннулированных и вытесненных версий.
3. Состояние «версия N+1 создана, рендер не закончен»: указатель текущей
   версии остаётся на N, пока рендер не удался.

### 4.2 Удаление против аннулирования

**Ключ — не статус, а связь с проведённой проводкой.** Первая редакция
предлагала «удалять черновики» по `status='draft'`, но такой статус бывает
только у сгенерированных документов: загруженные и пришедшие почтой живут в
цикле `inbox → recognized → linked → archived` и не удалились бы никогда.

Правило: документ удаляется физически, если **не существует** связи
`document_entries → journal_entries` со статусом `posted` или `reversed`.
Иначе — только аннулирование.

**Аннулирование хранится колонками** `voided_at`, `voided_by_user_id`,
`void_reason`, а не значением статуса. Значение `void` затёрло бы, был ли
документ `final` или `sent` — ровно то, что нужно аудиту, — и пересеклось бы
с существующим `archived`.

**Разобранные случаи:**

- документ на **черновой** проводке — удаляется, но факт пишется в аудит
  (`document_entries` каскадится, черновик останется без документа);
- **кадровый документ без связи с журналом** — по букве прошлой редакции
  подписанный трудовой договор мог быть физически уничтожен кадровиком.
  Нельзя: если на документ ссылаются `hr_orders.document_id` или
  `tax_filings.document_id`, доступно только аннулирование. Обе связи —
  `NO ACTION`, поэтому нарушение FK (SQLSTATE 23503) обязано отображаться в
  **409**, а не в 500;
- **объекты в S3** ни при удалении, ни при каскаде не удаляются. Либо
  появляется задача-сборщик, либо это явно объявляется политикой хранения.
  Молчаливая утечка объектов недопустима.

### 4.3 Отключение арендатора — исправление ошибки прошлой редакции

Прошлая редакция утверждала, что триггер `journal_entries_immutability()`
запрещает удаление непроведённой записи. **Это перевёрнуто.** В
`migrations/009_journal.sql` функция запрещает удаление записей со статусом,
отличным от `draft`; черновики удаляются свободно.

Скопировать исключение у `journal_lines_frozen_after_post()` тоже нельзя:
там оно означает «родительская запись уже удалена», а здесь удаляемая строка
и **есть** запись.

**Решение.** Физического удаления организации не будет: у `organizations`
уже есть статус `archived`, эндпоинта `DELETE` не существует, а проведённый
журнал обязан храниться (в РК — 5 лет). Штатное отключение арендатора =
`archived`.

**Область проблемы шире, чем считалось** (выяснено при релизе v0.3.1):
проведённая запись блокирует не только удаление организации, но и удаление
**пользователя**, который её создал — `created_by_user_id` объявлен
`ON DELETE SET NULL`, и этот `UPDATE` триггер тоже отвергает. То есть
сотрудника, однажды проведшего документ, невозможно удалить из системы.
Исключение обязано покрывать и этот случай, а тест — проверять оба.

Триггер всё же получает узкое исключение — **только** для очистки тестовых
данных, в форме:

```sql
IF NOT EXISTS (SELECT 1 FROM organizations WHERE id = OLD.org_id) THEN
    RETURN OLD;
END IF;
```

**Категорически запрещены два «простых» варианта:** `pg_trigger_depth() > 1`
(снимает неизменяемость внутри любого вложенного триггера) и сессионная
переменная вида `SET LOCAL app.allow_cascade` (вручает приложению рубильник
от insert-only журнала). Каскад проверяется **тестом**, а не рассуждением:
`reverses_entry_id` — самоссылка `NO ACTION`, `tax_filings.document_id` и
`hr_orders.document_id` — тоже `NO ACTION`.

## 5. Роль кадровика

### 5.1 Настоящее состояние RBAC — и почему наивное добавление роли опасно

Проверка по коду: контроль прав — это **запрет одного значения**,
`ctx.role == "viewer"`, в 23 местах девяти контроллеров. Это не «viewer не пишет»,
а денилист из одного элемента.

Следствие: добавление роли `hr` **проваливается открыто** — она пройдёт все
23 проверки и получит полный CRUD на журнал, налоги, зарплату и проведение
зарплаты в учёт. Кроме того, 21 из 47 org-scoped GET-маршрутов не проверяют
роль вообще, поэтому «— означает невидимо» из матрицы сегодня невыразимо.

Это тот же класс ошибки, что дал утечку в P2: механизм существовал, но не
был применён везде.

### 5.2 Что вводится

- `src/tenancy/OrgPermissions.hpp` — `allows(role, resource, action)`,
  **запрет по умолчанию**;
- макрос `API_REQUIRE_ORG_PERM` в `Guards.hpp` рядом с существующим
  `API_REQUIRE_ORG`;
- **23 замены** существующих проверок и **21 новая** на чтение, плюс два
  `download-url`-маршрута, которые объявлены POST, но по смыслу являются
  чтением;
- `is_valid_role()`, `OrganizationsController` (назначение роли участнику),
  `docs/openapi.yaml`, регенерация `schema.gen.ts`.

## 6. Навигация

Пунктов в авторизованном меню **десять** (прошлая редакция говорила девять):
Организации, Контрагенты, Журнал проводок, Документы, Сотрудники, Кадры,
Зарплата, Налоги, Администрирование, Аудит.

Группировка 3 + 3 + 1 + 3:

- **Учёт** — журнал проводок, документы, контрагенты
- **Кадры и зарплата** — сотрудники, кадры, зарплата
- **Налоги** — налоги
- **Настройки** — организации, администрирование, аудит

«Налоги» — вырожденный раздел из одного пункта: расчёты, сроки и ФНО внутри
`/taxes` являются вкладками, а не маршрутами. Принято оставить как есть.
`Главная` и `О сервисе` в группы не входят.

**Что мешает сделать это сегодня:**

1. У `RouteEntry` нет поля группы — нужны `navGroup` и **отдельный
   упорядоченный список групп**, иначе порядок разделов будет следовать
   порядку маршрутов.
2. Фильтрация по роли невозможна: `Nav.tsx` фильтрует по **глобальным**
   битам прав пользователя, а роль в организации (`org_members.role`) до SPA
   не доходит вообще — её отдаёт только `GET /orgs/mine`. Нужно отдавать
   org-роль в `/me` (или кэшировать `orgs/mine`), добавить `navRoles` и
   сделать предикат двухфакторным.
3. `Nav.tsx` рендерит ссылки **дважды** — десктоп и мобильное меню. Правило
   «пустой раздел не рисуется» обязано применяться к обоим.

## 8. Тестирование

- **Прописью:** все векторы §3.3 плюс краевые; отдельный тест, что
  отрицательное значение бросает; тест на границу триллиона.
- **Права:** на каждый закрытый для кадровика ресурс — тест на **403**,
  включая **GET**, а не только запись. Тест, что новая роль не проходит
  туда, куда не должна, — обязателен для каждого из 20 read-гейтов.
- **Прописи от клиента:** попытка прислать `*_words` → 422, в том числе на
  `POST /documents/generate`.
- **Правка:** соблюдает allowlist (422 на чужое поле); `uploaded`/`email`
  → 409; версия создаётся, старый PDF доступен; повторный рендер не
  перезаписывает файл и не снимает аннулирование.
- **Удаление:** документ без проведённой связи удаляется; со связью → 409 и
  доступно аннулирование; кадровый документ, на который ссылается приказ,
  не удаляется (23503 → 409).
- **Каскад:** удаление организации в тестовой очистке работает без ручного
  отключения триггеров.

## 9. Инварианты, которые фаза не имеет права нарушить

- деньги — целые тиыны, никакой плавающей точки и никакого обратного
  парсинга форматированных строк в деньги;
- ставки и константы только из `tax_rates`/`tax_constants`;
- `org_id` только из JWT, каждый запрос ограничен организацией;
- журнал insert-only, правится только сторно;
- 400 — форма, 422 — значение, 409 — состояние;
- тройная синхронизация маршрутов;
- весь пользовательский текст — русский;
- сборки только в GitHub Actions;
- коммиты без AI-атрибуции.
