
## Перед каждым деплоем: `helm dependency build`

`helm/*/charts/` — в `.gitignore`, то есть распакованные зависимости у каждого
оператора свои и **устаревают молча**. Если их не пересобрать, `helm upgrade`
берёт старые подчарты: значения совпадают, `helm diff` по значениям чист, а
манифест отличается.

Так при выкате v0.4.0 потерялся `S3_PUBLIC_ENDPOINT` — подписанные ссылки стали
подписываться внутренним адресом MinIO, и скачивание снаружи сломалось. Симптом
не связан с содержимым релиза, поэтому ищется долго.

**Всегда:** `helm dependency build` перед `helm upgrade`, и сверяйте
отрендеренный манифест с предыдущей ревизией, а не только значения.

## Ротация секрета: `helm upgrade` НЕ перезапускает поды

`checksum/config` в подчартах считается только по ConfigMap, но **не по Secret**.
А переменные вида `secretKeyRef` резолвятся один раз при старте контейнера.
Поэтому `helm upgrade`, меняющий только секрет, обновляет объект Secret и
завершается успешно, **оставляя поды работать со старым значением** — причём
Postgres не рвёт уже установленные сессии, так что всё выглядит здоровым.

**Всегда после ротации секрета:**

```
kubectl -n cyber-accountant rollout restart deploy/api deploy/worker
```

Если в том же обновлении меняется тег образа, поды перезапустятся сами — но
полагаться на это нельзя.

**Проверять ротацию по работающему процессу, а не по объекту Secret:**

```
kubectl -n cyber-accountant exec deploy/api -c cyber-accountant -- \
  sh -c 'printf "%s" "$JWT_SECRET" | sha256sum' | cut -c1-12
```

и сравнить с отпечатком секрета. Само значение не печатать.

## Публичные /ready и /health не доказывают доступ к БД

Ingress отдаёт `/` на `web:8080`, поэтому снаружи `/ready` и `/health`
возвращают HTML одностраничного приложения. Реальная проверка — обращение к
поду `api` внутри кластера, где `/ready` завязан на `SELECT 1`.

## values-cybercapybara.yaml НЕ является файлом боевого развёртывания

Название обещает обратное, и на этом легко подорваться. В репозитории лежат
**заглушки** (`test-db-pass-change-me`), другой хост БД и выключенный ingress.
Боевые значения существуют только внутри самого релиза Helm.

Развёртывание этим файлом ломает установку молча и до конца: пароли БД, Redis,
JWT, SMTP и S3 подставляются заглушками, чарт **удаляет секрет `api`**, а из
подов пропадают все `secretKeyRef`. Старые поды при этом продолжают работать —
они прочитали значения при старте, — поэтому сайт выглядит живым, хотя любой
перезапуск пода означал бы падение. Так был сломан выпуск 0.5.0 (релиз 23).

**Правильный способ получить боевые значения — извлечь их из последнего
удачного релиза:**

```
helm -n cyber-accountant get values cyber-accountant --revision <N> -o yaml > /tmp/vals.yaml
chmod 600 /tmp/vals.yaml            # файл содержит все секреты
# поменять только теги образов, затем:
helm upgrade cyber-accountant helm/cpp-env -n cyber-accountant -f /tmp/vals.yaml --wait
shred -u /tmp/vals.yaml
```

`helm history cyber-accountant` покажет номер последней ревизии со статусом
`deployed`. Никогда не запускать `helm upgrade` с `--reuse-values=false` и
репозиторным values-файлом.

**Признак, что это уже случилось:**

```
kubectl -n cyber-accountant get secret api    # NotFound == установка сломана
```
